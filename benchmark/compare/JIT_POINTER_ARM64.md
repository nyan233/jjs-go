# Static pointer checks for outlined JIT encoders

Measured 2026-11-24 on Apple M1 Pro (10 cores, 32 GiB), macOS 27.0.1,
Go 1.25.0 darwin/arm64, AC power, `GOMAXPROCS=10`.
Baseline: main `2813ca6`; implementation: `7ae1858` on
`codex/jit-inline-pointer-fallback`. No SSA changes are included.

## Implementation

The old pointer path used `jitEncodePointer` whenever the pointee could not
be inlined because of recursion, type cost or inline depth. Generated code
now always loads the pointer and checks for nil. The nil branch emits `null`
directly, using the existing reservation helper only when capacity is short.
`jitHelperPointer` and its Go implementation are removed.

Small pointees still inline as before. Recursive, large or deep pointees
use their separately compiled encoder through the existing `jitEncodeValue`
Go bridge. The bridge supplies the `ctx.data` write barrier and Go stack
check. Its child index is fixed during compilation; this is not interface
lookup or reflection dispatch. The outlined branch does not push another
root slot, so it also works at the maximum inline depth. Interface payloads
and custom marshaling retain their existing handling.

## Method

Both test binaries contain the same benchmark harness. The baseline binary
was built before changing production code. Compilation and warmup are outside
steady-state timing; the output buffer is reused. Five rounds alternate
which binary runs first, with 300 ms per steady-state case. Each cold sample
performs 50 fresh compilations, including code generation and loading; type
metadata and the process may already be warm. No builds, tests or profiles
ran concurrently with these benchmarks.

All 140 samples are retained in [before](jit-pointer-arm64-before.txt) and
[after](jit-pointer-arm64-after.txt); [metadata](jit-pointer-arm64-metadata.json)
records the revisions, binary hashes and commands. Tables show medians. This
is a desktop measurement; small changes and short cold runs are noisy.

| NilLarge | 27.07 | 25.17 | -7.0% | 27,408 | 27,504 |

| NilSlice128 | 768.20 | 597.80 | -22.2% | 928 | 1,136 |
| Leaves128 | 1,723.00 | 1,480.00 | -14.1% | 928 | 1,136 |

All cases remain at 0 B/op and 0 allocs/op after warmup. Code size is the
total generated code across all units for that type.

- InlineScalar is an already-inlined `*int` control and has unchanged code.
- NilRecursive and Recursive32 share a wrapper with fields before and after
  a recursive node pointer; Recursive32 has 32 nodes.
- NilLarge and Large point to a struct with 64 int64 fields, beyond the
  current inline-cost limit.
- NilSlice128 contains 128 nil node pointers. Leaves128 contains 128 non-nil
  nodes, each with a nil Next pointer.

NilSlice128 improves 22.2% and Leaves128 improves 14.1%; the latter benefits
from each leaf's nil Next path. The non-nil large and recursive examples
are essentially unchanged. Their child calls remain. Changed cases add
96–208 generated bytes, without expanding recursive bodies inline.

The extra instructions increase compiler allocations for changed layouts.
Short cold timings vary: even the unchanged InlineScalar control is 14.1%
slower in these samples, and nil/non-nil fixtures compile identical types.
These measurements do not establish a precise small cold-time improvement
or regression; they show no multi-fold increase like the SSA experiment.

## Validation

- The new nil-pointer test failed against the baseline when generic helpers
  were replaced with panic stubs, then passed after this change.
- Differential tests cover nil/non-nil recursive and large pointers, a
  1,024-node finite chain, six pointer indirections, interface payloads,
  custom marshalers, errors followed by reuse, and maximum inline depth.
- Outlined child calls run with forced argument spills, GC and stack growth.
- Native Go 1.22.12, 1.25.0 and 1.26.0 full test suites passed, along with
  comparison-module tests, ARM64 assembler tests and targeted race tests.
- The Windows amd64 compiler test binary cross-compiles successfully.
